# Deployment and email setup

This guide describes what the current website needs at launch. No domain, DNS, hosting or email changes are made by following the development setup. Confirm the provider and values for the actual deployment before changing DNS.

## Hosting

The site needs a Node.js server that can run Next.js 16, not static hosting alone. Confirm the selected plan supports Node.js 20.9.0 or later, the Next.js server, image optimization, the `/api/contact` route and outbound HTTPS requests to Resend. The planned Hostinger environment has not yet been verified.

Install the locked dependencies, build and start the application using the host's deployment process:

```bash
npm ci
npm run lint
npm run typecheck
npm test
npm run build
npm run start
```

Build with development dependencies available. The build may need network access to fetch Google fonts. The host must provide the public HTTPS domain and an appropriate process manager or managed application service. Set `SITE_INDEXABLE=false` before building a non-Vercel staging deployment. Production defaults to indexable; Vercel previews and development default to noindex. Keep private preview sites behind access controls as well, since robots rules are not access control.

## Website DNS and HTTPS

1. Identify the DNS provider controlling the domain's nameservers and take note of its existing records.
2. Obtain the exact A, AAAA or CNAME records for the apex domain and any `www` hostname from the selected hosting provider. Do not guess IP addresses or targets.
3. Add or update only the website records required by that provider. Keep existing email records unless the mailbox provider explicitly requires a change.
4. Enable HTTPS and verify the certificate. Confirm the chosen canonical domain and any `www` redirect.
5. Check that `src/config/site.ts` has the intended public origin before building. It currently uses `https://focustv.tv` for canonical URLs and the sitemap.

## Contact email

The contact form posts to `/api/contact`, which sends enquiries to `hammad@focustv.tv` through the Resend API. It does not create an inbox or reserve meeting times. The recipient mailbox must already exist and be reachable.

1. Create or access the Resend account and add a domain or subdomain controlled by FocusTV. Verify it for sending. Resend recommends a sending subdomain when appropriate.
2. Add the DNS records displayed for that domain in the Resend dashboard. These can include DKIM and SPF TXT records and an MX record for the return path. Use the exact names, values and priorities shown for the account; they depend on the selected domain and configuration. Check an existing DMARC policy and add or adjust one only as appropriate for the domain's current email setup. Avoid creating a second SPF record for the same hostname.
3. Preserve the existing mailbox provider's MX and authentication records; a Resend return-path MX is separate from the existing recipient mailbox setup. Do not change receiving mail to Resend unless that is intentionally planned.
4. Create a sending-only Resend API key, restricted to the verified domain if available. In the hosting provider's private environment settings, set:

   ```text
   CONTACT_FROM_EMAIL=Focus TV <sender@your-verified-domain>
   MAIL_API_KEY=<your-resend-api-key>
   ```

   The sender address above is an example: replace it with an address on the verified domain. Never commit the key or place it in client-side variables. The server sets the visitor's address as `reply_to`.

5. Redeploy or restart according to the host's environment-variable instructions. Send a real test through the deployed form and check the destination inbox, spam folder, sender and reply-to. Check the Resend dashboard if delivery fails. The automated tests use a mock and do not establish actual delivery.

## Proxy and rate limiting

The contact route checks the request origin against the host or forwarded host. It uses `x-vercel-forwarded-for` on Vercel and otherwise the last IP in `x-forwarded-for`; when no valid IP is available, requests share an `unknown` bucket. Its limits are five attempts per client and 30 per server instance in a ten-minute window. They are in-memory, reset on process restart and are not shared between instances.

Before launch, confirm that the hosting proxy safely sets the forwarded host and client IP headers, that legitimate requests pass the origin check, and that different clients are identified as expected. If the proxy cannot provide reliable client IPs or traffic requires shared protection, choose an appropriate host-level or shared rate-limiting solution for that deployment.

## Final checks

- Confirm `/robots.txt` and `/sitemap.xml` respond with the intended production domain and policy. They are generated by `src/app/robots.ts` and `src/app/sitemap.ts`; no duplicate static files are needed.
- Test all pages, redirects, mobile and desktop layouts, both themes, the gallery and Vimeo playback on the final domain.
- Confirm the documented hero-playback discrepancy and final content with the owner.
- Verify the contact success and error states without exposing credentials, and confirm the inbox receives the test.
- Review old website URLs and add approved redirects before switching traffic.
- Complete the Search Console, business-profile and live validation steps in [SEO and search visibility](SEO.md).
